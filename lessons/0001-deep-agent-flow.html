Why this is hard

Five things that break naive agents

① No gateAgent executes before a human sees the plan. Expensive, irreversible, too late to stop.
② No durable pauseApproval happens in one HTTP request. If it disconnects, the run is lost.
③ No async workerLong execution blocks a web thread. Timeout kills everything mid-run.
④ No concurrency guardTwo browser tabs approve at once. The graph executes twice. One result is silently lost.
✓ What we buildPlan gate → durable checkpoint → async approve → SQS queue → worker → SSE stream. Each piece solves one failure mode.

Step 3 deep-dive · interrupt()

The one primitive: interrupt()

When the node calls interrupt(), LangGraph serialises graph state to DynamoDB and raises a special exception. The HTTP response closes. Nothing is running.

def submit_plan(plan, thread_id):
    # Re-runs on EVERY resume — keep it pure
    human_decision = interrupt({
        "kind":         "plan_approval",
        "plan":         plan.model_dump(),
        "plan_id":      plan.plan_id,
        "interrupt_id": str(uuid.uuid4()),
        "owner_id":     owner_id,
    })
    # Only runs after resume
    if human_decision["type"] == "approve":
        return Command(update={...})
⚠ Re-run ruleEverything before interrupt() re-runs on every resume. A Slack notification placed there fires once per refine round.
✓ FixMove side effects after interrupt(), or make them idempotent — check whether the work is already done.
Why interrupt_id?A stale browser tab can hold the old plan_id. interrupt_id is minted fresh on each pause — it's the stronger stale-tab guard.
Steps 5–7 deep-dive · async approve

Why the approve endpoint returns 202

# POST /approve/async
gate = read_pending_interrupt(thread_id)   # from DynamoDB checkpoint
if gate["plan_id"]      != req.plan_id:      raise HTTPException(409)
if gate["interrupt_id"] != req.interrupt_id: raise HTTPException(409)
if gate["owner_id"]     != req.user_id:      raise HTTPException(403)

# Stage the resume decision — worker will read this, not us
persist_resume_decision(thread_id, {"type": "approve"})
put_run_state(thread_id, run_id, status="queued")
enqueue_deep_run(thread_id, run_id)        # SQS FIFO enqueue
return Response(status_code=202)           # returns immediately
Why 202?The graph doesn't run in this request. We just made approval durable and queued work. Returning 200 would imply the run completed — it hasn't.
Double-approve raceTwo tabs click Approve 50ms apart. Both try to write CLAIM#thread-123. DynamoDB conditional write — second loses, gets 409. Exactly one run proceeds.
Step 8 deep-dive · worker pickup ritual

Worker pickup ritual

msg = sqs.receive_message(QueueUrl=FIFO_URL, MaxNumberOfMessages=1)
thread_id, run_id = parse(msg)

claim_thread(thread_id)                    # distributed lock

with sse_manager.open(run_id) as stream:
    for event in graph.stream(
        input=None,                        # resume, not a new run
        config={"configurable": {"thread_id": thread_id}},
        stream_mode="values",
    ):
        stream.emit(event)                 # SSE: emit as events arrive

    put_run_state(thread_id, run_id, status="complete")
    release_claim(thread_id)
Keyinput=None means resume. LangGraph reads the staged resume decision from DynamoDB automatically — the worker doesn't pass it.
Common mistake · refine design

Refine: wrong vs right

✗ Wrong — LLM call inside the tool

def submit_plan(plan):
    while True:
        decision = interrupt({"plan": plan})
        if decision["type"] == "approve":
            return "approved"
        # BAD: separate out-of-band LLM call
        plan = call_llm_to_update_plan(
            plan, decision["feedback"]
        )
Two models now author the plan. Formats drift. Context is lost.

✓ Right — tool is a messenger only

def submit_plan(plan):
    decision = interrupt({"plan": plan})

    if decision["type"] == "approve":
        return Command(update={...})

    # Return feedback as a ToolMessage
    return Command(update={"messages": [
        ToolMessage(
            f"User wants: {decision['feedback']}\n"
            "Update todos. Call submit_plan again."
        )
    ]})
Agent reads the ToolMessage, edits its todos, calls submit_plan again. The agent loop IS the refine loop.

What to remember

The rules that survive production

interrupt() — everything before it re-runs on resume. Side effects must be after it, or idempotent.
interrupt payload — carry both human-readable plan data AND machine-checkable plan_id + interrupt_id.
async approve — stage the decision, enqueue to SQS, return 202. Never execute in the approve request.
refine = agent loop — the gate tool is a messenger. It passes feedback as a ToolMessage. The agent edits todos and calls submit_plan again.
worker pickup ritual — claim → SSE open → resume graph (input=None) → stream events → complete → release claim.
