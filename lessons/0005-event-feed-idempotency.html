Written at-least-once, shown exactly-once

The activity feed is a projection of the run, streamed over SSE. Two independent mechanisms — at-least-once delivery and crash-replay — both write every line twice. Making the user see each line once is the whole job.

The problem

Two ways every feed line gets written twice

At-least-once deliveryThe run rides an SQS FIFO queue. A worker that stalls past the visibility timeout or dies before deleting the message gets the run redelivered — the whole run, and its feed writes, happen again.
Crash-replay in a runResuming from the last checkpoint re-runs any node that started but did not commit — so it re-emits the feed lines it already emitted before the crash.

A naive "append a row per event" double-counts under both. The fix: give every row two values that behave in opposite ways on replay.

The keystone

Ordering and identity are different values

ValueAnswersOn replayWhere it comes from
seqIn what order?New every writeIn-process counter, seeded per pickup from the partition max
idem_keyHave I shown this?Identical{task_id}#{n} — execution position, never seq, never random

Exactly one of the two changes on replay, and exactly one does not. seq is also the reader's cursor and the browser's Last-Event-ID. Correctness only ever leans on idem_key.

Why the key survives a replay

idem_key = "{task_id}#{n}"

task_idOne node in one superstep. The curator parses it out of the event's checkpoint namespace ("{node}:{task_id}") — no hashing, no "which task is open" tracking, so parallel fan-out never misattributes.
nA per-task_id counter of the events that task emitted — #0, #1, #2 — reset fresh each time the keyer is built.

The trick: task_id keys on the checkpoint the node started from, not the one it writes. A crash-replay resumes from the same input checkpoint → same task_id → same key. A real loop iteration starts from a newer checkpoint → new task_id → counted as new.

The reader is dumb on purpose

A cursor and a set, doing different jobs

cursor (browser)Persisted as Last-Event-ID. Skips already-seen rows across reconnects — a fresh EventSource resumes from the last seq. Replay and live tail are one query; no history endpoint.
seen (API RAM)A per-connection set of idempotency keys. Skips crash-replay duplicates that land ahead of the cursor — they get new seqs, so only the repeated idem_key catches them.

The cursor advances even on a skipped row, so a mid-stream reconnect pages past the duplicates. The durable table keeps the duplicate rows; dedup is a read-time concern, thrown away when the connection closes.

A sharp edge in the counter

One stream must not poison another's keys

If a node emits two interleaved streams with different reproducibility — live "thinking" deltas (non-reproducible count) and deterministic frames (must reproduce) — one shared counter lets the noisy stream shift the quiet one's indices.

Attempt 1 · 5 deltasAttempt 2 replay · 3 deltas
shared counterstatus = taskB#5status = taskB#3 → new key → re-rendered
split ~cs bucketstatus = taskB#0status = taskB#0 → key reproduces → deduped

Live deltas count under {task_id}~cs; deterministic frames keep counting from #0. The rule: a counter-derived key may only count events whose count is itself replay-stable.

Don't conflate them

Three idempotency layers, three keys

LayerKey / mechanismGuards against
Event feedidem_key + reader dedupcrash-replay re-emitting the same activity line
Report emissionreported_cycle == cycle_stampredelivery double-reporting a report
Checkpoint / statedeterministic plan_id / provenance_ida replayed branch forking new state

All three: identity is deterministic (pure functions of their inputs), physical placement is not (seq, retry timing), and correctness only ever leans on the deterministic half.
